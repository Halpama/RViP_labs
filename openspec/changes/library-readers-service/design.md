# Design

## Context

Репозиторий содержит только базовый README и OpenSpec-конфигурацию, поэтому сервис создаётся как новый компонент в `apps/reader-service/`. Требования задают один источник истины в PostgreSQL: таблица `readers` создаётся миграцией, а API работает асинхронно. См. `proposal.md` для мотивации и `specs/library-readers/spec.md` для внешнего контракта.

## Goals / Non-Goals

**Goals:**

- Изолировать настройки, подключение к БД, ORM-модель, Pydantic-схемы и роутеры по указанным модулям.
- Обеспечить транзакционное изменение состояния читателя при выдаче/возврате книги и операциях с билетом.
- Сделать Docker Compose запуск воспроизводимым: PostgreSQL проходит healthcheck, затем миграция выполняется ровно один раз, после чего запускается API.
- Оставить миграции единственным механизмом создания схемы БД.

**Non-Goals:**

- Аутентификация, авторизация, пагинация, поиск и несколько книг на одного читателя.
- Ведение истории выдач, штрафов, авторов книг или дополнительных таблиц.
- Изменение статуса книги как отдельной сущности.

## Decisions

### Асинхронный HTTP и доступ к данным

FastAPI-роутеры будут использовать `async`-обработчики и SQLAlchemy 2.x `AsyncSession` с PostgreSQL-драйвером `asyncpg`. Это соответствует требованию неблокирующего API и позволяет применять единый session dependency с явным commit/rollback.

Рассматривались синхронный SQLAlchemy и SQLite: первый не соответствует асинхронному контракту, второй не соответствует требованию PostgreSQL в Docker и не проверяет реальные ограничения уникальности.

### Модель и целостность данных

ORM-модель будет отражать только `readers`; уникальность `card_number` закрепляется и в ORM-описании, и ограничением миграции. `card_active` получает значение `true`, `registered_at` — серверное время регистрации, `book_title` допускает `NULL`. Роутеры выполняют бизнес-проверки перед изменением и обрабатывают конфликт уникальности как 409.

Состояние книги не будет изменяться через общий PATCH: специализированные операции выдачи и возврата сохраняют инварианты активного билета и максимум одной книги.

### Миграции и жизненный цикл контейнеров

Alembic будет использовать async-шаблон, а `env.py` читать `DATABASE_URL` из окружения. В приложении не будет вызова `Base.metadata.create_all`. Compose разделит `postgres`, одноразовый `migrate` (`alembic upgrade head`) и `api`; `migrate` зависит от healthcheck PostgreSQL, а `api` — от успешного завершения миграции.

### Конфигурация и контракты

Настройки будут загружаться из окружения через `DATABASE_URL` и порт приложения с безопасными локальными значениями только там, где это не скрывает ошибку подключения. Pydantic-схемы зададут валидацию входных данных, а ответы будут возвращать стабильные поля читателя и сводки. Ошибки отсутствующего ресурса, бизнес-конфликта и валидации будут различаться кодами 404, 409 и 422.

### Docker и локальный запуск

Dockerfile будет собирать сервис из `apps/reader-service`, устанавливать `requirements.txt` и запускать Uvicorn. Корневой Compose-файл будет публиковать API на `3001`, PostgreSQL — на `55432` для локального доступа, а внутренние контейнеры будут использовать имя сервиса БД и порт `5432`. README опишет оба режима запуска и Swagger на `/docs`.

## Risks / Trade-offs

- [Risk] Два параллельных запроса могут одновременно пройти проверку «книги нет» → Mitigation: выполнять проверку и изменение в одной транзакции с блокировкой строки читателя (`SELECT ... FOR UPDATE`) для state-changing операций.
- [Risk] Переменная `DATABASE_URL` может отсутствовать или иметь неподдерживаемую схему → Mitigation: валидировать конфигурацию при старте и явно завершать запуск с диагностикой.
- [Risk] Удаление читателя может стереть сведения о выданной книге → Mitigation: блокировать удаление читателя с книгой и возвращать HTTP 409.
- [Risk] Compose может запустить API до готовой схемы → Mitigation: healthcheck PostgreSQL и условие успешного завершения контейнера миграций.

## Migration Plan

1. Собрать образы и поднять PostgreSQL.
2. Дождаться healthcheck и выполнить единственную Alembic-миграцию в сервисе `migrate`.
3. Запустить API только после успешной миграции; локальный режим выполняет те же шаги вручную.
4. Для отката приложения остановить Compose-сервисы и развернуть предыдущий образ; откат схемы выполнять отдельной Alembic-командой только после проверки совместимости данных.
