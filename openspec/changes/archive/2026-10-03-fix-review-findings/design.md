# Design

## Context

Сервис уже реализует FastAPI-маршруты поверх одной таблицы `readers`, а существующая capability задаёт коды 404, 409 и 422. Основной дефект находится на границе PATCH-схемы и API-контракта; дополнительные замечания относятся к тестовой изоляции, воспроизводимости зависимостей и документации.

## Goals / Non-Goals

**Goals:**

- Сделать PATCH-схему закрытой и разрешить только непустые изменения профиля.
- Закрепить контракт сценариями API и базы данных, включая все перечисленные 404/409/422 и summary-варианты.
- Сделать сборку и запуск воспроизводимыми на поддерживаемых ОС и зафиксировать результаты проверки.

**Non-Goals:**

- Не менять маршруты, коды успешных ответов или бизнес-схему: остаётся одна таблица `readers`.
- Не добавлять конкурентные тесты, новые таблицы, Liquibase или новый слой миграций.

## Decisions

1. **Закрытая Pydantic-модель PATCH.** Удалить поля состояния из модели обновления, включить `extra="forbid"`, оставить профильные поля строковыми с запретом `null` и пустых значений и отклонять пустой объект без обновляемых полей. Это сохраняет управление состоянием только в специализированных операциях; ручная фильтрация payload менее надёжна и допускает расхождение со схемой.
2. **Тестировать поведение через HTTP и отдельный database regression test.** API-тесты покрывают наблюдаемый контракт и конфликты, а database-тест сохраняет идентификатор до rollback либо перечитывает запись после rollback. Все команды pytest явно используют `TEST_DATABASE_URL=postgresql+asyncpg://library:library@localhost:55432/library_test`; критерием является ноль skipped. Это избегает обращения к expired ORM-экземпляру и не требует изменения модели.
3. **Фиксация версий без изменения стека.** В `requirements.txt` используются точные совместимые версии текущих библиотек, выбранные только после проверки существования версии и установки в чистом venv; Docker-образы получают только существующие patch-теги Python 3.13 slim и PostgreSQL 16 alpine, подтверждённые `docker compose build` и `docker compose config`. Диапазоны оставляют непредсказуемые обновления и не устраняют замечание ревью.
4. **Документация по ОС и процессу.** README разделяется на Windows, macOS и Linux с одинаковым Compose-потоком и OS-специфичной активацией venv. `docs/ai-process.md` фиксирует только реально выполненные команды и их фактические результаты, а промпты propose для первой и второй задач оставляет как `вставить автором`; также документирует пересмотренные решения (Alembic вместо Liquibase, override entrypoint migrate, CRLF entrypoint, поиск `.env`) и проверяемые результаты.
5. **Конкурентность вне объёма.** Row locking уже является частью реализации, но новые тесты гонок не добавляются; это явно отмечается в tasks.md, чтобы не смешивать отдельный объём работ с исправлением ревью.

6. **Синхронизация проектных инструкций.** После реализации обновляются `AGENTS.md` и `.github/copilot-instructions.md`, чтобы правила PATCH и обязательный запуск тестов с указанным `TEST_DATABASE_URL` и нулём skipped не расходились с change.

## Risks / Trade-offs

- [Risk] Точные версии могут устареть → обновлять их отдельным намеренным изменением с прогоном полного набора проверок.
- [Risk] Локальные команды зависят от PostgreSQL и Docker → README явно указывает `TEST_DATABASE_URL`, healthcheck и порядок миграций.
- [Risk] Сценарии API могут загрязнять общую тестовую БД → использовать существующие фикстуры очистки и проверять пустое состояние перед summary-тестами.

## Migration Plan

Изменение не требует миграции базы данных. После обновления зависимостей выполнить миграции штатной командой, запустить тесты с `TEST_DATABASE_URL`, затем проверить `docker compose config`, `docker compose up --build` и сценарий Swagger. Откат выполняется возвратом к предыдущим файлам приложения и конфигурации; схема БД не затрагивается.
